# PACE-to-LIBERO faithfulness audit

**Status: blocked before implementation and evaluation.** This audit applies
the project's reproduction rule: an algorithmically material choice must come
from the PACE primary source or official author code, not from a new local
interpretation.

## Sources and code availability

- Primary source inspected: Junnan Nie et al., *PACE: Phase-Aware Chunk
  Execution for Robot Policies with Action Chunking*,
  [arXiv:2606.00537v2](https://arxiv.org/abs/2606.00537), accessed 2026-08-19.
- The paper's HTML and arXiv source page contain no author code/project URL.
  A targeted search for an author-provided PACE repository found no official
  implementation. CatalyzeX lists the work as “Request Code”, rather than
  linking public code. Third-party descriptions were not used as an algorithm
  source.
- Therefore, the paper is the only available source of implementation detail.

## What the primary source specifies

At query \(i\), PACE receives a full chunk

\[
\mathbf A_i = \pi_\theta(o_{\tau_i},\ell) \in \mathbb R^{L\times d_a},
\qquad h_i \in \{1,\ldots,L\}.
\]

It executes \((a_{i,1},\ldots,a_{i,h_i})\), discards the suffix, and queries
again at \(\tau_{i+1}=\tau_i+h_i\). It is one scalar/global horizon: gripper
commands, if present in the environment action, use the same selected prefix
as the arm. The paper profiles only executed arm groups \(b\in\mathcal B\):

\[
\mathbf v_i^b = \psi_b(\mathbf A_i) \in \mathbb R^{L-1},
\qquad \tilde{\mathbf v}_i^b = \mathcal S(\mathbf v_i^b).
\]

Candidates are low-speed valleys \(\mathcal V_i^b\subseteq
\{1,\ldots,H_{\max}\}\), subject to a minimum temporal separation. The
source names a valley prominence score \(\Phi_i^b(r)\) and accepts

\[
\mathcal R_i = \bigcup_{b\in\mathcal B}
 \{r\in\mathcal V_i^b:\Phi_i^b(r)\geq\delta_\mathcal T\}.
\]

The selection rule is exact:

\[
h_i =
\begin{cases}
\min \mathcal R_i, & \mathcal R_i\ne\varnothing,\\
H_{\max}, & \mathcal R_i=\varnothing.
\end{cases}
\]

For multiple arms, the paper pools accepted candidates and chooses the
earliest one. In a single-arm setting, \(\mathcal B\) contains that arm only.
It says \(\delta_\mathcal T\) is calibrated once per task from training
demonstrations only, without evaluation rollouts, success labels, or
fixed-horizon sweeps.

Published RoboTwin simulation uses \(L=50\). The default reported
hyperparameters are \(d_{\min}=10\) and calibration percentile \(\rho=5\).
The sensitivity table also reports \(d_{\min}\in\{5,10\}\) and
\(\rho\in\{0,5,10,25\}\). The paper calls \(d_{\min}\) the minimum candidate
spacing and says larger \(\rho\) makes acceptance stricter.

## Material details not specified by the primary source

The paper leaves the following as named operators or qualitative descriptions;
it does not give equations, pseudocode, or values that determine them:

| Required detail | What is published | Missing determination |
|---|---|---|
| \(\psi_b\), joint profile | “arm-specific kinematic profiling operator” | Whether it is successive joint-position difference, a norm, an interval scaling, or another construction. |
| Cartesian profile | A Cartesian raw/smoothed ablation is reported | Cartesian pose representation, translation/rotation metric or weighting, and whether poses are generated by forward kinematics. |
| Smoothing \(\mathcal S\) | “suppress short-range fluctuations” | Filter type, window width, padding, and parameters. |
| Local valleys | “low-speed valleys” with minimum separation | Local-minimum rule, edge handling, and whether separation is applied before or after ranking candidates. |
| Prominence \(\Phi\) | “pronounced deceleration relative to surrounding motion” | Prominence equation, neighborhoods, and units. |
| Calibration \(\delta_\mathcal T\) | A per-task percentile \(\rho\) from demonstrations | Population being percentiled, percentile direction, handling of no valleys, and the equation mapping it to \(\delta_\mathcal T\). |
| \(H_{\max}\) | Only \(H_{\max}\leq L\) and fallback to \(H_{\max}\) | A numeric default or rule for selecting it. The paper's examples have \(L=50\), but do not state that \(H_{\max}=50\). |

These omissions are not cosmetic: they change selected horizons, the
calibration threshold, and the fallback schedule. The published default
\((d_{\min},\rho)=(10,5)\) is insufficient to derive a deterministic
algorithm.

## Verified LIBERO action contract

The frozen path is current LeRobot `0.6.2` at commit
`f66e5128ecb2456e8c54a63d15404fa59c16aebc`, `hf-libero 0.1.4`, and
`robosuite 1.4.0`. It uses LIBERO `ControlEnv` with `OSC_POSE` and a Panda arm.
The existing runner configures `control_mode: relative`; LeRobot sets
`robot.controller.use_delta = True` after reset.

The full postprocessed ACT chunk is `(100, 7)`. Each 7-D action is bounded in
the policy/environment interface by `[-1,1]` and has:

| Indices | OSC_POSE meaning | Controller scaling |
|---|---|---|
| `0:3` | relative end-effector position command `(x,y,z)` | `[-1,1]` is linearly scaled to `[-0.05,0.05]` metres |
| `3:6` | relative end-effector axis-angle orientation command `(ax,ay,az)` | `[-1,1]` is linearly scaled to `[-0.5,0.5]` radians |
| `6` | gripper command | outside PACE's arm profile |

Robosuite adds the scaled translation to the current end-effector position and
updates orientation by composing the axis-angle delta with the current
orientation. Thus these six channels are delta controls, not a predicted joint
trajectory or a sequence of absolute Cartesian poses. Translation has metres
and orientation has radians. A direct `norm(action[0:6])` would mix those
units; choosing a conversion weight would be a new method, not a reproduction.

An ideal pose reconstruction would also require a source-defined integration
convention and, still, a source-defined metric combining successive position
and orientation changes. The PACE paper's Cartesian-profile description does
not provide either. Its default is a **joint-space** profile specifically
because it matches the source policy action space; this LIBERO ACT policy does
not emit joint-space actions.

## Reproduction decision

**Do not implement or evaluate PACE on this path.** A faithful scalar/global
PACE baseline is blocked by two linked ambiguities:

1. The primary source and available official materials do not uniquely define
   the deterministic valley-selection/calibration algorithm.
2. The source does not define a Cartesian kinematic profile applicable to a
   relative position-plus-axis-angle action chunk. The paper's preferred
   joint-space profile cannot be applied because this policy has no joint-space
   action output.

No PACE code, calibration, synthetic PACE unit test, smoke rollout, or 230
episode evaluation was run. Implementing any of them would require inventing a
speed metric, smoothing/valley/prominence procedure, calibration semantics, or
\(H_{\max}\), which is outside the faithful-reproduction scope.

## Minimum unblocker

An author-provided implementation or written specification must define all of:
the kinematic profile (including a Cartesian pose metric), smoothing,
local-valley/prominence computation, percentile-to-threshold calibration, and
\(H_{\max}\) policy. For LIBERO specifically, it must also state how the
relative 6-D OSC command is converted to the required kinematic trajectory.
